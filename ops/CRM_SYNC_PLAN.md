# CRM → сайт: план синхронизации объектов (+ типы, «Продано»)

Цель (по твоим решениям): всё ведётся в CRM, на сайт объекты попадают под твоим
контролем — кнопки **«Опубликовать на сайт» / «Снять с публикации»**, **массовые**
действия, статус **«Продано»** (объект остаётся на сайте с плашкой «Продано» вместо
«Срочно»), снятие с публикации — просто убирает объект. Типы:
`APARTMENT / HOUSE / COMMERCIAL / LAND`. Валюта только **TJS**. Риелторы — только
роль **AGENT**. Новые типы по умолчанию **скрыты** (тумблер в админке сайта).

## Почему это не сделано в этой сессии (два блокера)
1. **Репозиторий CRM (`D:\CRM`) не открыт в этой рабочей папке** — код кнопок и
   массовых действий живёт там, отсюда я его не правлю. Нужно открыть меня в `D:\CRM`.
2. **Нужна миграция боевой БД** (MySQL) — добавить 2 колонки в `listings`. Это ты
   просил делать осознанно, поэтому не применяю вслепую; сделаем в плановом деплое.

## Что уже сделано на сайте (безопасно, без миграции)
- Плашка **«Продано»** на странице объекта (поле `sold` уже есть в БД, проброшено
  во фронт). Показывается вместо «Срочная», когда объект продан.

## Что осталось на СТОРОНЕ САЙТА (этот репозиторий)
1. **Схема БД** — `db/schema.ts`, таблица `listings`, добавить:
   ```ts
   published: boolean("published").default(false).notNull(),
   category: mysqlEnum("category", ["APARTMENT","HOUSE","COMMERCIAL","LAND"])
     .default("APARTMENT").notNull(),
   externalId: varchar("external_id", { length: 100 }), // id объекта в CRM (для upsert)
   ```
   Затем `npm run db:generate` → миграция → применить на проде (`db:migrate`) в деплое.
   Валюта: отдельного поля нет — цены целые, отображаются как «с.» (сомони/TJS),
   так что «только TJS» соблюдается само собой.
2. **Публичная выдача** — `api/listing-router.ts`, в `list`/`getById` добавить
   фильтр `published: true` (снятые с публикации никогда не видны). Проданные
   показывать (с плашкой), неопубликованные — нет.
3. **Приёмный эндпоинт для CRM** (Hono, не tRPC), в `api/boot.ts` + новый
   `api/crm-sync-router.ts`, авторизация по общему секрету `CRM_SYNC_API_KEY`
   (по аналогии с лид-ключом), приним��ет одиночные и **массовые** операции:
   ```
   POST /api/v1/crm/listings   (заголовок X-Api-Key)
   body: { items: [ { externalId, action: "publish"|"unpublish"|"sold", data? } ] }
   ```
   — `publish` → upsert по `externalId`, `published=true`;
   — `unpublish` → `published=false`;
   — `sold` → `sold=true` (остаётся видимым с плашкой).
   Маппинг из CRM: только тип из 4 категорий, только агенты с ролью AGENT, TJS.
4. **Тумблер видимости типов** — хранить в `cms_entries` (ключ `categoryVisibility`,
   значение `{APARTMENT:true, HOUSE:false, COMMERCIAL:false, LAND:false}`), новый
   экран/переключатели в админке сайта, фронт фильтрует каталог по видимым типам.
5. **Фронт** — плашка «Продано» на карточках (Home, ListingsPage, Favorites,
   AgentDetail), фильтр по категориям в каталоге.

## Что нужно на СТОРОНЕ CRM (репозиторий `D:\CRM`)
- Кнопки **«Опубликовать на сайт» / «Снять с публикации»** на карточке объекта.
- **Массовые действия** в списке (выбрать несколько → опубликовать/снять/пометить проданным).
- Смена статуса → «Продано».
- Клиент, который дёргает `POST /api/v1/crm/listings` сайта с `CRM_SYNC_API_KEY`,
  маппит поля CRM → поля сайта, фильтрует агентов по роли AGENT и валюту TJS.
- Секрет `CRM_SYNC_API_KEY` — одинаковый в `.env.production` сайта и CRM (как уже
  сделано для лид-ключа).

## Порядок безопасного внедрения
1. Site: схема + миграция (на тесте/локально), приёмный эндпоинт, фильтр `published`.
2. Site: тумблер видимости + категории на фронте.
3. CRM: кнопки, массовые действия, вызов эндпоинта.
4. Прогон на паре объектов → массовая публикация → плановый деплой обоих проектов.
